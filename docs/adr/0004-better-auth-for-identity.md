# ADR-0004: Better Auth owns the identity schema

Status: Accepted
Date: 2026-09-19

## Context

Every table in `packages/database` already assumed a real `organization_id`/membership concept
enforced server-side (spec §1 non-negotiable: tenant isolation on every read/write, never trust a
client-supplied tenant ID). Until now that was two hand-rolled tables (`organizations`,
`memberships`) with nothing actually authenticating or populating them — building Phase 1's job
engine on top of that would mean faking org IDs and redoing authorization later.

Better Auth's `organization` plugin models exactly this (org, member, invitation, role) on top of
its own user/session/account tables, so the choice was: hand-roll auth on our own tables, or adopt
Better Auth and let it own that slice of the schema.

## Decision

1. **Better Auth owns identity.** `packages/database/migrations/0001_better_auth_schema.sql` is
   generated by Better Auth's own CLI, not hand-written, and must never be hand-edited — regenerate
   it instead (see the header comment in that file for the exact command). It defines `user`,
   `session`, `account`, `verification`, `organization`, `member`, `invitation`.
2. **UUIDs, not Better Auth's default string IDs.** `advanced.database.generateId: "uuid"` in
   `apps/api/src/auth.ts` makes every Better Auth primary key a real UUID
   (`pg_catalog.gen_random_uuid()`), matching every table we'd already written. Confirmed by
   actually running the generator against a live DB and inspecting the output — not assumed.
3. **Postgres via the built-in Kysely adapter, not Prisma/Drizzle.** `database: new Pool({
   connectionString: process.env.DATABASE_URL })` — Better Auth auto-detects the dialect from the
   raw `pg.Pool`. This keeps `packages/database` a plain-SQL, framework-free migrations folder for
   everything else, rather than forcing an ORM into the stack for one library.
4. **Everything else is renumbered and repointed, not replaced.** The former `0001_init.sql` is now
   `packages/database/migrations/0002_platform_tables.sql`: the hand-rolled `organizations`/
   `memberships` tables are deleted, and every `organization_id` FK (in `projects`,
   `agent_profiles`, `tasks`, `artifacts`, `audit_events`) now references Better Auth's
   `"organization"` table. `projects.owner_member_id` became `owner_user_id`, referencing `"user"`
   directly — a project owner is a specific person, not an org-membership row, and the column
   should say so.
5. **Better Auth lives in `apps/api`, not a shared package.** It's tightly coupled to one live
   Postgres connection and the Fastify server that already owns identity per the spec's service
   table. Mounted at `/api/auth/*` via the officially documented Fastify integration pattern
   (`fromNodeHeaders` + `auth.handler` + a Fetch API `Request`/`Response` bridge) in
   `apps/api/src/index.ts`.
6. **No sign-in method is enabled yet.** `auth.ts` only configures the database, ID generation, and
   the organization plugin — no `emailAndPassword`, no OAuth providers. Confirmed live: a sign-up
   attempt correctly returns `EMAIL_PASSWORD_SIGN_UP_DISABLED` rather than silently succeeding or
   erroring. Which sign-in method(s) to offer is a separate, later decision (Phase 6 customer
   experience), not bundled into this change.

## Verification performed

Not just "it compiles" — actually run against a live local Postgres (`infrastructure/docker-compose.yml`,
remapped to host port 5433 to avoid an unrelated project's container already on 5432):
- Generated `0001_better_auth_schema.sql` for real via `pnpm dlx auth@1.7.5 generate` against an
  empty DB, confirmed UUID PKs and the exact table/column names before writing any FK-repointing
  edits (not guessed in advance).
- Applied `0001` then `0002` against a clean DB — clean apply, no FK errors, proving the UUID-id
  assumption and the repointed references actually line up.
- Confirmed `projects`' foreign keys resolve to `organization` and `"user"` via `pg_constraint`.
- Booted `apps/api` for real and hit three live routes through the Fastify mount: `/health` (200),
  `/api/auth/get-session` (200, `null` for anonymous), `/api/auth/organization/list` (401
  Unauthorized for anonymous) — proving the mount works generically across GET/POST and that the
  organization plugin's routes are genuinely wired in, not just present in the type signature.

## Consequences

- Identity schema is no longer ours to hand-edit. Every Better Auth upgrade means regenerating
  `0001_better_auth_schema.sql` and re-diffing it against `0002`'s FK assumptions.
- `apps/web`'s session/org UI (client-side `better-auth/client` + `organizationClient()` plugin)
  is still unwired — explicitly deferred to Phase 6, not silently forgotten.
- Which sign-in method(s) to enable (email/password, OAuth, magic link) is now the next open
  decision, not resolved by this ADR.
