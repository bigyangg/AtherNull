## 0. Validated against research (2026-09-19)

These confirm or adjust the spec's §11 "proposed defaults":

| Decision | Spec default | Research finding | Action |
|---|---|---|---|
| SDK integration | Pinned Python dependency | Confirmed. `pip install -U openhands-sdk openhands-tools` (matched pair, Python ≥3.12), MIT licensed. `openhands.workspace` already ships Local/Docker/Remote sandbox abstractions matching §6. Verified live: real install of pinned 1.42.1 + `from openhands.sdk import LLM, Agent, Conversation, Tool` imports clean. | Proceed as planned. |
| Sandbox isolation | "Dedicated host or stronger VM/microVM isolation" (undecided) | Plain `DockerWorkspace` isolation is undocumented/unhardened — treat as container-level only, not a security boundary. Firecracker/Kata need `/dev/kvm` + nested virtualization, which most non-bare-metal VPS don't expose (AWS needs `.metal`; DO/Azure/GCP often support it — **must confirm with Coolify VPS provider**). gVisor (`runsc`) runs as a Docker runtime swap, no bare metal needed, is the standard recommendation for shared multi-tenant untrusted-code hosts. | **[!] Decide**: gVisor-hardened Docker for MVP; Firecracker only if KVM/nested-virt confirmed available later. Daytona's "Runtime for OpenHands" is a hosted fallback to unblock the demo without building sandbox infra at all. |
| Model selection | Single `model` per agent profile | User requirement (2026-09-19): not locked to one provider, and must route to cheaper/pricier models by task complexity automatically, not just let clients hand-pick a model. | **Decided**: ADR-0003 (`docs/adr/0003-cost-complexity-model-routing.md`). `agent_profiles.model` → `model_tiers`; routing computed by the orchestrator/API at dispatch time via `packages/model-router` (v1 rule-based heuristic, unit tested), never inside the worker. |
| Auth / identity | Not specified in spec §11 | User requirement (2026-09-19): needed a real org/session/membership layer before Phase 1's tables (which all assume `organization_id`) mean anything. | **Decided**: ADR-0004 (`docs/adr/0004-better-auth-for-identity.md`). Better Auth owns identity via its `organization` plugin on the same Postgres instance (Kysely+`pg.Pool`, no new ORM); identity schema is generated by its CLI, never hand-written. Verified live end-to-end, see Phase 0.5 below. |

Open from spec §11 still needing validation: backend runtime choice (TypeScript API — team preference, not yet decided), database isolation approach beyond RLS testing, verification authority/dispute process owner, Solana payments (devnet contract not yet written/audited), repository access consent flow, retention TTLs.

## 1. Non-negotiables (carry into every phase, don't relitigate)

- Agent never gets host SSH, Docker socket, prod DB creds, or escrow signing keys.
- PostgreSQL is the money/state source of truth; Redis is queue/cache only.
- A worker reports results; it cannot self-approve or release funds.
- Tenant isolation enforced server-side on every read/write/download — never trust a client-supplied tenant ID.
- No deployment or payment counts as successful until the authoritative system confirms it.

- [x] **Phase 5 — Payments (Solana devnet)** — 4E.1 funding + activation gate

- [x] **Phase 6c — Discuss before funding** — sign in lands in the canvas;

- [x] **Phase 6 — Customer experience** — agent-first canvas
  (`/projects/[id]`): one conversation from prompt -> plan -> budget -> devnet
  funding -> live agent -> verification -> review -> on-chain settlement, with

- [~] **Phase 7 — Reliability and demo** — one-command stack
  (`pnpm dev`), dependency-free demo repo, demo runbook. Still: devnet
  rehearsal incl. refund path, recordings, backup/restore and crash drills.
- [~] **Phase 8 — Multi-rail payments (ADR-0022)** — architecture accepted;
  provider rollout remains gated. Preserve Solana as the only build escrow
  rail. No x402 charge until pricing and the product, network, asset,
  facilitator/finality, replay, reconciliation, and refund/dispute decisions
  are complete.
  - [~] **8.1 — Capability contract** — shared modes and operations; provider
    operations must be explicitly supported. In progress; no provider routing
    or payment behavior changes.
  - [ ] **8.2 — x402 product and settlement decisions** — decide the exact
    customer-facing paid operation, pricing/units, network/asset, facilitator,
    payment confirmation, idempotency/replay protection, and refund/dispute
    behavior. No charge work before this gate.
  - [ ] **8.3 — x402 ledger and verification design** — settle provider-evidence
    schema, tenant attribution, append-only audit requirements, duplicate
    handling, reconciliation, and outage/ambiguous-result behavior; keep it
    separate from the Solana funding and settlement ledgers.
  - [ ] **8.4 — x402 implementation** — implement only the approved one-shot
    operation, explicit provider selection, payment confirmation before
    fulfillment, safe replay handling, and reconciliation. Do not expose
    worker/internal or usage-summary endpoints as billable; do not permit x402
    to satisfy the build activation gate.
  - [ ] **8.5 — x402 validation and staged rollout** — automated tests for
    retries, replay, pending/failed/ambiguous confirmation, reconciliation,
    tenant isolation, and unsupported capabilities; then runbook, observability,
    and a disabled-by-default rollout.
  - [ ] **8.6 — Stripe evaluation and implementation** — begin only after
    x402 is stable; decide Stripe authorization/capture/refund/dispute and
    ledger/reconciliation semantics before integrating. No implicit fallback
    between providers.

**Go/no-go gate** (spec §10): don't add marketplace bidding, multi-chain, autonomous prod deploy, or more agent types until one coding job reliably produces a verified patch within budget and survives retries.
